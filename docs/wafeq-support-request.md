# استفسار تقني: ربط Accounting API بالمرحلة الثانية واسترجاع QR وXML

السلام عليكم فريق وافق،

نطوّر نظامًا داخليًا لصحيفة سبق لإنشاء العملاء وعروض الأسعار والفواتير، مع مزامنة السجلات المحاسبية إلى وافق وإخراج الفواتير بتصميمنا.

لدينا نظام سابق ينشئ الفاتورة محاسبيًا عبر `POST /v1/invoices/`، ثم يحاول تغيير حالتها إلى `FINALIZED`. وفق مراجعة شيفرته، يحاول الإبلاغ عبر `POST /v1/zatca/simplified-invoices/report/`، واسترجاع الحالة والرمز عبر `GET /v1/invoices/{id}/zatca/`. وصف هذه المحاولات لا يثبت نجاح الإبلاغ أو اعتماد الهيئة.

مسار `POST /v1/invoices/{id}/tax-authority/report/` الوارد في توثيقكم **ليس مستخدمًا في النظام السابق**. أعددناه في موصل HR الجديد محليًا، لكنه لم يُختبر بإرسال فاتورة فعلية. نحتاج تأكيد ملاءمته لمنشأتنا ولنوع المستند، وخطوات الانتقال الصحيحة، بحيث تبقى **فاتورة محاسبية واحدة** دون إنشاء مستند ضريبي مكرر.

نرجو تزويدنا بالتوثيق الحالي ومثال استجابة منقّح يوضح:

1. ما تسلسل الإنشاء والاعتماد/الإبلاغ المدعوم للفواتير القياسية والمبسطة ضمن Accounting API؟ هل يلزم تغيير الحالة إلى `FINALIZED` قبل الإبلاغ؟ وكيف نسترجع نتيجة الهيئة النهائية وأسماء حقولها وقيمها، ونتعامل مع `PENDING` وإعادة المحاولة دون تكرار؟
2. كيف نسترجع **QR الرسمي، وXML المعتمد أو الموقع، وUUID وتجزئة الفاتورة** المرتبطة بمعرف الفاتورة المحاسبية نفسه؟ وما صيغة QR: حمولة TLV بصيغة Base64 أم صورة؟
3. ما الطريقة المعتمدة لإصدار نسخة بتصميمنا مع تسليم XML الرسمي أو تضمينه في PDF/A-3؟
4. هل يتطلب ذلك تفعيلًا إضافيًا على منشأتنا أو صلاحيات/اشتراكًا معينًا؟ وهل تتوفر بيئة اختبار لهذه الدورة دون إنشاء فواتير إنتاجية؟

جرّبنا للقراءة فقط المسار القديم `GET /v1/invoices/{id}/zatca/` على فاتورة أمكن استرجاعها عبر مسار الفاتورة العادي، وكانت نتيجة المسار القديم **HTTP 404**. لا نفترض أن ذلك يحدد البديل؛ نرجو تأكيد ما إذا كان السبب متعلقًا بالمسار أو صلاحيات/تفعيل المنشأة، وتحديد الطريقة المدعومة حاليًا.

النظام السابق يستطيع توليد QR احتياطي محلي وXML محلي، وقد يضع `REPORTED` افتراضيًا عند غياب الحالة. لذلك لن نعتمد هذه القيم المحلية لإثبات قبول الهيئة، ونحتاج المخرجات الرسمية المرتبطة بالفاتورة الخارجية نفسها. كذلك لم يثبت أن PDF المحلي بصيغة PDF/A-3 أو يتضمن XML الرسمي.

لا نحتاج إلى تبادل أي مفاتيح API أو بيانات عملاء في الرد؛ يكفي توثيق ومثال اصطناعي أو منقّح.
