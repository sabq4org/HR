# تجربة الحسابات والملف والإجازة

هذه الدفعة تضيف دخولًا بحسابات داخلية وتحقيقًا بخطوتين وحفظًا دائمًا. تبقى البيانات اصطناعية إلى اعتماد أصحاب البيانات والاستضافة والسياسة والأرصدة. المعاينة العامة لا تُحوّل تلقائيًا إلى وضع الحسابات.

## إعداد نسخة محلية مستقلة

1. اضبط إعدادات خاصة متجاهلة من Git: `HR_MODE=operational`، ومفتاح `HR_DATA_KEY` ثابت بطول 32 بايت بصيغة base64url، و`HR_SEED_SYNTHETIC=false`. لا تطبع المفتاح في محادثة أو سجل؛ احفظه في مدير الأسرار المعتمد. فقده يمنع قراءة الملفات وأسرار المصادقة.
2. SQLite المحلية تستخدم `.data/hr-operational.sqlite` افتراضيًا. PostgreSQL يستخدم `HR_DB_DRIVER=postgres` و`DATABASE_URL` ومخطط `hr_operational` المستقل. لا تستخدم مخططات المعاينة أو قاعدة الأخبار.
3. أنشئ ملف JSON خاصًا بصلاحية `0600` خارج Git يحوي مصفوفة من سجلين مختلفين؛ الأول `role: "hr"` والثاني `role: "approver"`. لكل سجل الحقول `name`, `employeeNumber`, `email`, `title`, `department`, `location`, `joinDate` بصيغة `YYYY-MM-DD`. استخدم أشخاصًا اصطناعيين في التجربة؛ الأسماء والصلاحيات الحقيقية يحددها المالك.
4. نفّذ `npm run accounts:bootstrap -- /secure/identities.json /secure/invitations.json`. يقبل الأمر قاعدة خالية فقط. يحفظ روابط تفعيل مفردة الاستخدام في ملف جديد بصلاحية `0600`، دون طباعتها. فشل حفظ الروابط يعكس عملية إنشاء الحسابين.
5. شغّل `npm run dev` محليًا، أو ابنِ باستخدام `npm run build` ثم `npm start`. افتح رابط التفعيل من الملف الخاص. اربط تطبيق المصادقة، واختر كلمة مرور، وأدخل رمزه ثم احفظ رموز الاستعادة في مكان خاص. لا تشارك رابط حساب مع شخص آخر.
6. بعد التفعيل، سجل الدخول بكلمة المرور ورمز تطبيق المصادقة. الرمز المستخدم للتفعيل لا يعاد استخدامه؛ انتظر الرمز التالي أو استخدم رمز استعادة مرة واحدة.

لا يمنح التمهيد أرصدة إجازة أو رواتب، ولا يؤكد التصنيف التعاقدي. ينشئ الحد الأدنى من الملف لأصحاب الصلاحية كي يستكملوا الهيكل والملفات والسياسات. لا يوجد مسار تهيئة علني في API.

## استعادة الوصول

رموز الاستعادة تستخدم مرة واحدة مع كلمة المرور. يمكن إصدار مجموعة جديدة باستخدام رمز مصادقة حديث؛ تُلغى المجموعة السابقة. إعادة ضبط حساب آخر وتغيير الصلاحيات يتطلبان التحقق الإضافي بحسب الإجراء، ولا يسمح النظام بتعطيل آخر مسؤول HR أو آخر معتمد نشط من داخل التطبيق.

عند فقد كل العوامل أو انتهاء رابط التفعيل الأول، يتحقق المشغل المخول من الهوية خارج النظام ثم يضع طلبًا خاصًا بصلاحية `0600` يحوي `employeeId` و`reason` (سبب إداري موثق دون بيانات حساسة). ينفذ `npm run accounts:recover -- /secure/recovery-request.json /secure/invitation.json`. هذا مسار محلي للمشغل، بلا endpoint عام. يلغي الجلسات وكلمة المرور والمصادقة والرموز القديمة، ويصدر رابطًا جديدًا في ملف خاص ضمن المعاملة؛ فشل حفظ الملف يعكس التغيير. سلّم الرابط عبر قناة داخلية معتمدة ثم أزل نسخته المؤقتة وفق سياسة الأسرار.

## تجربة القبول

- HR ينشئ ملف مدير وملف موظف اصطناعيين. تغيير الدور يمر باعتماد مستقل؛ يحدد المدير المباشر في الملف.
- HR يجهز سياسة إجازة بمصدر وفترة سريان وأيام عمل وعطل. المعتمد المستقل يعتمدها. ثم يجهز HR إسناد السياسة والرصيد الافتتاحي، ويعتمده شخص مستقل قبل ترحيل الرصيد؛ لا يؤخذ الرصيد من مثال افتراضي. يمكن رفض الإسناد أو سحبه قبل الاعتماد. الإسناد المستقبلي يظل معلقًا حتى بداية سريانه، فلا تصبح أرصدته متاحة مبكرًا.
- ينشأ الحساب ويربط الموظف مصادقته. يجرب الاطلاع على ملفه وطلب إجازة، ثم المدير وHR يقرران وفق صلاحية المورد.
- يجرب إلغاء إجازة معتمدة أو تمديدها أو عودة مبكرة بطلب مستقل. يتحقق HR من الحركات المقابلة وثبات القرار الأصلي ومنع تكرار الأثر عند إعادة الإرسال.
- يعطل حساب الموظف، ثم يتحقق من رفض جلساته القائمة. تُختبر الاستعادة والتغيير المستقل للأدوار والتدقيق.
- في «حالة التشغيل» يراجع المختص آخر دورات التنبيه. التنبيهات داخلية؛ لا يرسل النظام بريدًا أو رسالة نصية.

## بوابة الاستضافة الفعلية

الاستضافة العلنية لوضع الحسابات تتطلب PostgreSQL مخصصًا، أصل HTTPS صريحًا في `HR_PUBLIC_ORIGIN`، ومفتاحًا دائمًا مستقلًا. يرفض التشغيل بذور الشخصيات الاصطناعية على المضيف العلني. يجب مراجعة إعدادات الحسابات والنسخ الاحتياطية والاستعادة والاحتفاظ والصلاحيات قبل بيانات الموظفين؛ لا يكفي تغيير متغير اتصال.

الرواتب النظامية والمرضية ذات الأثر المالي ونهاية الخدمة والتوقيع والتكاملات الحكومية خارج قبول هذه الدفعة. يظل اختيار قاعدة Neon الحالية وموضع الاستضافة قرار تشغيل مستقلًا. دليل النسخ والتراجع والتنبيهات في `docs/operations-runbook.md`، والأدلة المنفذة في `STATE.md`.

## التوافق مع النسخة الخاصة القائمة

يبقى `HR_MODE=private-hosted` ببوابة كلمة المرور ومخطط `hr_private` منفصلًا عن وضع الحسابات `operational`. الدمج لا يحوّل مستخدمي النسخة الخاصة أو بياناتهم تلقائيًا. أداة `private:access` السابقة تظل أداة مشغّل موثوق لتلك النسخة، وليست مسار ويب للمستخدمين؛ صلاحيتها المباشرة على قاعدة البيانات خارج مسار الاعتماد الثنائي للحسابات الجديدة.

إذا كان للموظف رصيد افتتاحي أو حركة سابقة، يُسند التقويم والسياسة برصيد إضافي صفر. تعديل الرصيد يمر بطلب تسوية مستقل؛ لا يسمح المساران بإضافة رصيد افتتاحي ثانٍ، بما فيه الرصيد الصفري المسجل سابقًا.
